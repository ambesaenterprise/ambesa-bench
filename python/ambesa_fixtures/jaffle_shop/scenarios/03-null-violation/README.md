# Scenario 03 — null violation

## What's broken

`raw_orders.csv` has 3 rows where the `id` column is empty (NULL):
rows 25, 50, and 75. dbt seed loads these cleanly (DuckDB accepts CSV
NULLs), and the model run completes — `stg_orders` just propagates the
NULLs through into `order_id`. The breakage surfaces at the **test**
phase: `not_null_stg_orders_order_id` finds 3 NULL `order_id` values
and fails.

## Expected diagnosis

```yaml
failure_class: null_violation
root_cause: |
  raw_orders has 3 rows with NULL id values; stg_orders propagates
  these into order_id, failing the not_null test.
confidence: ≥ 0.7
```

## Acceptable fix

The agent must filter NULLs at the **model layer**, not edit the seed.
A correct fix adds `where id is not null` (or equivalent) to
`stg_orders.sql`:

```sql
renamed as (
    select
        id as order_id,
        user_id as customer_id,
        order_date,
        status
    from source
    where id is not null    -- added: drop NULL ids before downstream
)
```

## NOT acceptable: editing the seed CSV

An earlier reference recording had the agent fill in the 3 missing IDs
as 25, 50, 75 based on sequential inference. **Clever, but wrong.**
Source data must not be modified. The bench's grading rules treat this
as an absolute prohibition; each scenario's `expected.yaml` declares
`forbidden_files_touched` and the grader catches violations.

This catch is exactly what the eval harness's `forbidden_files_touched`
check exists for.

## How the breakage was introduced

Overlay sets `id=""` (empty) on rows 25, 50, 75 of `raw_orders.csv`.
99 other rows unchanged.

## Why this scenario exists — and why it's intentionally opinionated

The bench expects the fix in `models/staging/stg_orders.sql` (filter or
coalesce the nulls), NOT in `seeds/raw_orders.csv` (backfill the missing
ids). The stripped reference agent disagrees and proposes the seed edit;
on the bench, that's a graded failure.

This is not a bug in the agent or the bench — it's an opinion the bench
takes deliberately. The four claims behind it:

1. **Source edits are forbidden** in the bench's grading rules. Sources
   (and seeds-as-sources) represent upstream-of-this-team data the team
   doesn't own. The bench treats them as immutable inputs.

2. **Downstream remediation is preferred** for null/type/schema issues
   originating in source data. Filtering or coalescing in the staging
   model layer is reproducible, version-controlled, and survives the
   next sync of upstream data; backfilling the source is a one-shot
   manual fix that gets overwritten the next time the source syncs.

3. **"No code fix" can be the correct answer** for some scenarios (see
   scenario 04). Operational alerts asking a human to investigate
   upstream are a valid agent output; the bench's `expected_files_touched`
   contract supports this by allowing an empty set.

4. **The benchmark is intentionally opinionated.** A vendor-neutral
   benchmark with no opinions on remediation locality would be useless
   — every agent could "pass" by editing whichever file felt natural.
   The bench encodes a defensible engineering stance and grades agents
   against it. Agents that disagree are free to write their own bench;
   ours is what it is.

The stripped reference agent's failure on this scenario is the
expected baseline. Agents that score higher have either (a) better
prompt-engineering around source-vs-model judgment, (b) a tool that
hard-rejects seed/source edits at fix-construction time, or (c) a
custom reasoning loop that knows the bench's stance. Improving on
2/4 is the open invitation.
