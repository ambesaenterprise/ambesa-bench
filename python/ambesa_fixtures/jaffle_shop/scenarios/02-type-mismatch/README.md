# Scenario 02 — type mismatch

## What's broken

Upstream changed `raw_payments.amount` from integer cents (e.g., `1000`) to
dollar-formatted strings (e.g., `$10.00`). dbt seed still loads — DuckDB
just infers the column as VARCHAR. But `stg_payments.sql` does:

```sql
amount / 100 as amount
```

Dividing a VARCHAR by an integer raises a DuckDB type error:

```
Conversion Error in model stg_payments
  Could not convert string '$10.00' to BIGINT
```

Downstream `orders` then fails because its `ref('stg_payments')` is dead.

## Expected diagnosis

```yaml
failure_class: type_mismatch
root_cause: |
  raw_payments.amount changed from integer cents to dollar-formatted
  string ($10.00). stg_payments still divides by 100 assuming cents.
confidence: ≥ 0.7
```

## Acceptable fixes

The agent has flexibility here — anything that makes `dbt build` succeed
and produces dollar amounts in `stg_payments.amount` is fair game:

1. **Cast + drop the /100** (preferred — recognizes values are now dollars):
   ```sql
   cast(replace(amount, '$', '') as decimal(10, 2)) as amount
   ```
2. **Cast and keep /100** (technically wrong but applies cleanly; would
   fail downstream tests if they existed):
   ```sql
   cast(replace(amount, '$', '') as decimal(10, 2)) / 100 as amount
   ```

The grader's contract pins **what file is touched** + **diff applies cleanly**
+ **failure_class is correct**, not the exact SQL. Both shapes pass.

## How the breakage was introduced

Overlay swaps the seed's amount column from `1000` (int cents) to `$10.00`
(string dollars). 113 rows. No other change to the project.
